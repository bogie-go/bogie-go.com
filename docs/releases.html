v0.6.8 31 Oct 2026

  • When goose refuses a migration because its file is older than the newest one already applied (an "out-of-order" migration), the error now says what to do: rename the new file with a timestamp after the newest one, if no other database has applied it yet. It reads migrate: up: detected 1 missing (out-of-order) migration lower than database version (...): version 20200101000000: a migration file is older than the newest one already applied; rename the new file with a timestamp after it (only if no other database has applied it yet). See Models and migrations.
  • The header of a generated factory no longer says it is only ever written once: model:sync merges a new column's default into it and keeps your edits.
  • Existing apps: bogie app:update adds app/services/migrate/ specs and the new error wording. Nothing to move. See Moving an app from v0.5.5 to v0.6.8.

v0.6.7 31 Oct 2026

  • The job role in config/deploy.production.yml is cmd: worker, as v0.6.6 made it in deploy.yml. v0.6.6 missed this file, so a production deploy still ran blog blog worker, which starts the web server instead of the worker.
  • The status alias asks the web role only (app exec --reuse -r web ...). It ran on every role, and a job container serves no HTTP, so it failed there. See Deploying.
  • Existing apps with jobs: bogie app:update changes both deploy files, but if you have already put your own host in them it leaves conflict markers on the job lines. Keep your host and set cmd: worker. See Moving an app from v0.5.5 to v0.6.8.

v0.6.6 31 Oct 2026

  • The job role's cmd in config/deploy.yml is worker, not blog worker. The image's ENTRYPOINT is already the binary, so the old line ran blog blog worker, which prints unknown command "blog"; serving instead and starts a second web server where the worker should have run. Apps made with --jobs, or given jobs by g job, had the old line. The file's comments now say when app exec takes the binary name (with --reuse, which runs in the container that is up) and when it does not (without it, Kamal starts a new container through the ENTRYPOINT).
  • This release fixes deploy.yml only; v0.6.7 fixes the production overlay, so move straight to v0.6.8.

v0.6.5 30 Oct 2026

  • The generated test/testapp has a Put(path, body), beside Get, Post, Patch and Delete. See Request specs.
  • Existing apps: bogie app:update adds it to test/testapp/testapp.go.

v0.6.4 30 Oct 2026

  • In generated Create and Update, a references column whose foreign key names nothing (Postgres 23503) is ErrInvalid ("post_id does not exist"), like a duplicate value, so a controller answers 422 where it answered 500. g model writes a CreateX spec for it on a model with a reference.
  • Existing apps: re-run g model (or g scaffold) for a resource that has a references column to get it; the files you changed are reported conflict until you pass --force.

v0.6.3 30 Oct 2026

  • A uuid attribute in an app with the default bigint ids writes db/adapter/uuid.go (parseUUID and uuidString). Before, the store did not compile (undefined: parseUUID) because only a --id=uuid app had that file. model:sync writes it too, when a new column is a uuid.
  • model:sync tells a uuid column from a string one, so an untouched uuid field no longer shows as a change.
  • g job --pretend writes nothing, and on an app with no jobs it no longer adds --jobs first: it says this app has no app/jobs yet; --jobs would be added first and lists what the job would create.

v0.6.2 30 Oct 2026

  • A namespaced g scaffold_controller admin/products writes views of its own, app/views/admin_products.go (AdminProductRequest, AdminProductResponse, AdminProductsResponse), flat and prefixed like a model, instead of sharing the public views. g scaffold admin/products already did, so the two agree. d scaffold_controller removes those views.

v0.6.1 30 Oct 2026

  • model:sync removes a field only when a migration dropped or renamed away its column. A field you added with no column, such as a count or a joined name, now stays.
  • With conflict markers in a file, model:sync no longer runs sqlc, which would only fail on them.

v0.6.0 30 Oct 2026

  • New command bogie model:sync [TABLE]: after a migration, generated or hand-written, it adds the model field for each new column and removes the field for each dropped one, and merges the regenerated queries, store and factory into your copies. Validate and everything else of yours stays. See Models and migrations.
  • New attribute modifier :null for a column that may be NULL: a pointer in the model, and *time.Time for a datetime through db/adapter/nullable.go. g scaffold refuses it for now.

v0.5.6 28 Oct 2026

  • The adapter suite is named "Adapter", generated comments say "model" where they said "domain", and route-group variables are camelCase for a two-word controller or namespace.
  • The exit status 1 that go run adds after an app has already said what failed is dropped.
  • Factories note that their datetime defaults are placeholders.

v0.5.5 28 Oct 2026

  • The "is mounted" spec that g controller writes for a stub, in an app or in a namespace, now looks the method and path up in app.Server.Router.Routes() instead of sending a request and expecting anything but a 404. A real Show or Destroy answers 404 for a record that is not there, and that must not break the spec once the action is written. It still fails when a route was never registered or the namespace lost its mount line. A route with an id is now titled GET /posts/:id, not /posts/1. See Request specs.
  • Generated Go names for a multi-word resource are camelCase, not snake_case: apiKeys := router.Group("/api_keys"), apiKeyFromRow, and productCategories in the list handler and its view function, where v0.5.4 wrote api_keys, api_keyFromRow and product_categories. g authentication api_key writes apiKeyFromRow too. Types, file names, routes and tables are unchanged.
  • Existing apps: bogie app:update from v0.5.4 changes AGENTS.md and bogie.toml; the generated code you have stays and still builds. Re-run a generator to get the new shape. See Moving an app from v0.5.0 to v0.5.5.

v0.5.4 28 Oct 2026 Breaking

Breaking for an app that has a namespace made by v0.5.0 to v0.5.3. The namespace package is now plural, app/controllers/admin_controllers/, like every other directory. The old admin_controller/ package keeps working after app:update, but bogie doctor does not list it, and the next g controller admin/NAME writes a second package that does not build. Rename the package first; the steps are in Moving an app from v0.5.0 to v0.5.5. New apps are not affected.

  • g scaffold admin/pages is a model of its own: the model is admin_page, the table admin_pages, and its PagesController sits in the namespace at /admin/pages. d scaffold handles the namespaced form. For a controller over an existing model, use g scaffold_controller.

v0.5.3 28 Oct 2026

  • g scaffold --only ACTIONS writes just the actions you list, with their routes, store methods, views and request specs; the model half is always whole. bogie g scaffold category name:string:uniq --only index,show mounts GET /categories and GET /categories/:id and nothing else.
  • New generator g scaffold_controller [NS/]RESOURCE: the HTTP half of a scaffold over a model that already exists, mounted in a namespace if you give one. It reads the attributes back from app/models and shares the model's views file, which only gains the types it lacks. --only works here too, and d scaffold_controller removes the controller, its spec and the emptied namespace package. See Resources, controllers and routing.

v0.5.2 28 Oct 2026

  • The commented example Context in a generated model spec now compiles where you uncomment it: the model variable and its BeforeEach are declared at the Describe.

v0.5.1 27 Oct 2026

  • New positioning: Bogie is "A Go API service, from zero to production." The README, docs, templates, help text and generated code no longer compare Bogie to Rails, and docs/FROM_RAILS.md is gone from the repository. The commands, the layout and their decisions are unchanged. The authentication generators now describe a trusted service and any JWT library rather than a specific app.
  • g model also writes the model's own spec, app/models/<name>_test.go. It starts from the factory's defaults, so a rule added to Validate that the defaults break fails there, and it shows where the next rule's Context goes. d model removes it with the model, and a new app ships the app/models suite.
  • Generated not-found specs read as sentences: DescribeTable("returns ErrNotFound") with the entries "when the id is not a number" ("a uuid" in a uuid app), "when the id is empty" and "when no <model> has that id", for both Get and Delete. Generated comments say what a rule is instead of pointing at a numbered rule the reader cannot see.
  • Existing apps: bogie app:update brings in the template changes. Specs that generators wrote earlier stay as they are; re-run a generator for a resource to get the new ones. See Moving an app from v0.5.0 to v0.5.5.

v0.5.0 27 Oct 2026 Breaking

Breaking The layers of a generated app moved, and bogie app:update cannot follow the move on its own: it exits with a conflict in app/models/models.go and leaves the old files retired. See Moving an app from v0.4 to v0.5 for the steps.

  • app/domain/ (the types and their Validate) is now app/models/. The hand-written Store, withTx and row conversion that lived in app/models/ are now db/adapter/ (package adapter). sqlc writes to db/sqlc/ (package sqlc) instead of beside the store, and the store qualifies sqlc's types as sqlc.Post and sqlc.CreatePostParams. g model, g scaffold, g authentication, g seed and d write and remove the new paths.
  • withTx now hands its closure the pgx.Tx as well as the bound queries: func(tx pgx.Tx, q *sqlc.Queries) error, so a hand-written store method no longer has to reach into sqlc's unexported field to get at the transaction.
  • The bin/ci step that runs sqlc diff is called "Schema: sqlc current" (it was "Schema: models current"); it checks db/sqlc.

v0.4.2 27 Oct 2026

  • Generated store specs are organised by what they test: each store method is its own Describe (GetPing, ListPings, UpdatePing, DeletePing), a Context names the situation, and every It names the model ("finds the ping by id", "includes the saved ping", "removes the ping"), so a failure reads as a sentence.
  • The comments in the generated model type describe ids without assuming uuid: they are int64 under the default scheme and string under --id=uuid.
  • Existing apps: only comments and newly generated specs change; there is nothing to move. Re-run a generator for a resource to get the new spec shape.

v0.4.1 24 Oct 2026

  • Generated apps test with Ginkgo v2 and Gomega: Describe, Context, BeforeEach, It and Expect, in external _test packages. Each package has one <pkg>_suite_test.go that owns its shared setup (app in controllers and requests, store in models). See Testing and CI.
  • g model also writes a factory, test/factories/<table>.go. g controller and g scaffold write request specs beside the controller, through the wired Server, instead of fake-store controller tests. g service, g job and g authentication write specs too.
  • A new app's go.mod requires github.com/onsi/ginkgo/v2 and github.com/onsi/gomega.
  • Existing apps: commit, then bogie app:update. It adds the suites and test/, moves the scaffold's own tests to Ginkgo and tidies in the two modules. Tests that generators wrote earlier, and app/models/store_test.go (reported retired), are left as they are. See Moving an app from v0.3 to v0.4.

v0.4.0 24 Oct 2026

  • New apps get test/: testdb (a clean, migrated test database per test), testapp (the whole app on it, with a request helper), factories (with Sequence for unique values) and requests (a starter GET /healthz request test). g authentication token adds As(subject) to sign a test request in.
  • app/models/store_test.go and its testStore are gone. g model's store test is package models_test on testdb.Store.
  • go test runs one package at a time (-p 1), in bogie test, make test and bin/ci, because the packages share one test database.
  • Existing apps: go straight to v0.4.1.

v0.3.2 22 Oct 2026

  • bogie g config database username=xxx password=yyy adds keys to the app's own server and database groups. Those groups are never created or removed: bogie d config database is refused.
  • Values are written bare when YAML reads them as the string they are (username: xxx) and quoted otherwise; a bool key takes yes/no/on/off.

v0.3.1 22 Oct 2026

  • bogie g config hello=world (or retries:int=3) adds a flat top-level key, a field directly on Config, overridden by HELLO.
  • New top-level entries are inserted in alphabetical order in both the credentials file and the Config struct; keys inside a group keep the order typed.

v0.3.0 22 Oct 2026

  • New: bogie g config GROUP key[:type][:flag][=value] ... adds a typed group to the credentials file, a struct in config/<group>.go; bogie d config GROUP removes it. Types string, int, bool, duration; flags req, secret. See Configuration.
  • The credentials file is nested groups (server:, database:, token:), with no section named after the app.
  • g authentication keeps its secret in a group: token.secret, control.secret.

Breaking Setting variables lose the app prefix: BLOG_DATABASE_URL is now DATABASE_URL, BLOG_ADDR is SERVER_ADDR, BLOG_TOKEN_SECRET is TOKEN_SECRET. Only BLOG_ENV, BLOG_CREDENTIALS, BLOG_MASTER_KEY, BLOG_CONFIG_DIR and BLOG_TEST_DATABASE_URL keep it. What to do: for an existing app, rename those variables in your shell, CI and deploy config, and move each credentials file from the flat blog: section into groups with bogie credentials:edit (and -e production). See Upgrading an app.

v0.2.13 22 Oct 2026

  • Deleting a row something else still references now returns domain.ErrInvalid ("product is still in use"), so a controller answers 422 instead of a raw foreign-key error and a 500.
  • Existing apps: re-run g model to get the new Delete.

v0.2.12 21 Oct 2026

  • Every new app's app/models/store.go has a withTx helper: it begins a transaction, runs your function against a *Queries bound to it, and commits on success or rolls back on error. Call it from a hand-written method in <table>_extra.go for writes that span tables. The app's AGENTS.md has a new "Run a transaction" section.
  • Removed dead code (IDScheme.idSQLCType) that golangci-lint flagged.
  • Existing apps: commit, then bogie app:update to get withTx.

v0.2.11 20 Oct 2026

  • A brand-new app passes bin/ci again: app/models/id.go is gofmt-clean and parseID is used, which v0.2.9 and v0.2.10 apps failed before their first model.
  • Adding public/index.html no longer fails the generated routes_test.go; a new test checks it is served at /.
  • bogie server live-reloads on .html edits. See Static files and error pages.
  • Create and Update on a model with a :uniq column return domain.ErrInvalid ("email is already taken") on a duplicate, not a raw database error and a 500.
  • Existing apps: commit, then bogie app:update for the template fixes; re-run g model for a model with a :uniq column.

v0.2.10 18 Oct 2026

  • The two files g model overwrites whole, db/queries/<table>.sql and app/models/<table>.go, now open with a comment saying so and naming the sibling file for your own code: <table>_extra.sql for a hand-written query, <table>_extra.go for a store method. See Hand-written code beside generated code.
  • Existing apps: the comment appears the next time g model rewrites a table's files. A query you added inside a generated .sql file should move to <table>_extra.sql before then.

v0.2.9 18 Oct 2026

  • New apps get bigint ids by default (an auto-incrementing bigserial), as Rails does, instead of uuid. bogie new NAME --id=uuid keeps uuids. The choice is app-wide, recorded in bogie.toml, and every later generator and app:update follows it. See Id schemes.
  • Existing apps have no id line in bogie.toml, which reads as uuid, so they stay on uuid and nothing changes. Leave that line out rather than adding id = "bigint".
  • A scaffolded Update now loads the record first and reuses its id, instead of building the id from the URL string. New scaffolds get it; an existing one keeps working under uuid as it is.
  • The generated routes_test.go no longer fails golangci-lint (a comment read as a malformed go:embed directive).

v0.2.8 17 Oct 2026

  • An app's own public/index.html now answers at /, in every environment. Before, / always fell through to the development welcome page or the 404. See Static files and error pages.
  • The generated 404.html and 500.html show the Bogie mascot, styled like the welcome page.
  • Existing apps get both through bogie app:update.

v0.2.7 17 Oct 2026

  • New public/ folder, embedded in the binary: a request no route answers is tried against a file there, then the development welcome page, then public/404.html. A panicking handler gets public/500.html. To serve a favicon or robots.txt, drop it in public/ and widen the go:embed line in public/public.go.
  • Hand-written store methods now go in a sibling file, app/models/<table>_extra.go, because g model rewrites app/models/<table>.go whole. See Models and migrations.
  • Existing apps get public/ through bogie app:update.

v0.2.6 17 Oct 2026 Breaking

Breaking Seeds are no longer goose SQL files with a version table. db:seed:rollback, db seed-down, make db-seed-down and make g_seed_* are gone. What to do: commit, port any existing seed SQL into db/seeds/*.go by hand, then run bogie app:update for the new runner; it moves the layout but does not translate seed content. Write each seed so a second run changes nothing. See Upgrading an app.

  • Seeds are plain Go: bogie g seed NAME writes db/seeds/<name>.go and registers it; bogie db:seed runs every seed, every time, so each must be safe to run twice. bogie d seed NAME takes one out. See Seeds.

v0.2.5 16 Oct 2026

  • New bogie routes, like rails routes: every mounted route with its method, path and handler, read from the booted app. It prints in development only. Existing apps get it through bogie app:update.

v0.2.4 16 Oct 2026

  • A field with no type defaults to string, as in Rails: bogie g model comment title body:text.
  • string now becomes Postgres varchar instead of text, keeping the distinction Rails makes. Only new migrations are affected; existing ones keep whatever type they already say.

v0.2.3 13 Oct 2026 Breaking

Breaking The test environment now reads only <APP>_TEST_DATABASE_URL, never <APP>_DATABASE_URL, so tests and bin/ci can no longer empty a development database. What to do: a CI setup that points tests at a database through <APP>_DATABASE_URL must rename it to <APP>_TEST_DATABASE_URL. Existing apps get the fix through bogie app:update. See Upgrading an app.

  • A scaffolded PATCH changes only the fields sent; before, it blanked the rest. New scaffolds get it; an existing scaffolded Update needs the change by hand (the release notes show the few lines).
  • bogie server and bogie worker stop the app they started on SIGTERM.
  • bogie help lists the authentication generator; the request log shows path=/ for the root.
  • Docs: using your own Postgres without Docker (see Your own Postgres), a code of conduct and a security policy.

v0.2.2 6 Oct 2026

  • When the database cannot be reached, the error now says which of the common causes it is (nothing listening, credentials refused, or the database never created) and what to run, keeping the original error underneath.

v0.2.1 6 Oct 2026

  • bogie app:update adds the tool directives that newer templates pin, such as Air for live reload, so an older app reloads after updating without a manual go get -tool.

v0.2.0 6 Oct 2026

  • Live reload: in development bogie server and bogie worker run under Air, rebuilding and restarting on save. Production runs the compiled binary.
  • bogie g job works on an app made without --jobs, adding River first.
  • New apps need Go 1.26, pinned in the template (the tool itself builds with 1.25).

v0.1.0 3 Oct 2026

  • The first release: bogie new (with --jobs for River), the generators migration, model, scaffold, controller, service, job and authentication, bogie destroy, bogie doctor and bogie app:update.
  • Generated apps ship credentials, migrations, bin/ci, a Dockerfile and Kamal 2 config, a welcome page and AGENTS.md.
  • Installed with go install only; no Homebrew tap.

Older history, before the first tag, is in the commit log.
