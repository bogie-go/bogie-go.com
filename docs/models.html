Models and migrations

Rails's Post is one class that is a table, a type and a query builder. Here that is three files, each with one job, plus the migration, a spec and a factory. One command writes all six:

bogie g model post title body:text

A field with no :type is a string, as in Rails, so title is title:string.

      create  db/migrate/20261003053152_create_posts.sql
      create  db/queries/posts.sql
      create  app/domain/post.go
      create  app/models/posts.go
      create  app/models/posts_test.go
      create  test/factories/posts.go
         run  sqlc generate

The migration

goose SQL, timestamped, embedded in the binary:

-- +goose Up
CREATE TABLE posts (
    id         bigserial   PRIMARY KEY,
    title      varchar     NOT NULL DEFAULT '',
    body       text        NOT NULL DEFAULT '',
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);

-- +goose Down
DROP TABLE posts;

Every generated column is NOT NULL with a type-appropriate default, so sqlc emits plain Go types rather than pointers. A column that truly needs null is one edit to the migration, by hand.

The queries

db/queries/posts.sql, named statements that sqlc compiles:

-- Written by `bogie g model`: overwritten whole on the next run. A
-- hand-written query goes in posts_extra.sql, not here.

-- name: GetPost :one
SELECT * FROM posts WHERE id = $1;

-- name: ListPosts :many
SELECT * FROM posts ORDER BY created_at DESC, id DESC LIMIT $1;

-- name: CreatePost :one
INSERT INTO posts (title, body) VALUES ($1, $2) RETURNING *;

-- name: UpdatePost :one
UPDATE posts SET title = $2, body = $3, updated_at = now() WHERE id = $1 RETURNING *;

-- name: DeletePost :execrows
DELETE FROM posts WHERE id = $1;

A query that names a column which does not exist fails at make sqlc, not in production.

The domain type

app/domain/post.go imports nothing third-party (rule 3). In the default bigint scheme an id is an int64; in an --id=uuid app it is a string, which the store turns into a uuid:

type Post struct {
	ID        int64
	Title     string
	Body      string
	CreatedAt time.Time
	UpdatedAt time.Time
}

// Validate is the model's validations, as Rails would put them. Wrap every
// failure in ErrInvalid so a controller can answer 422 without knowing the
// rule:
//
//	return fmt.Errorf("%w: title is required", ErrInvalid)
func (p Post) Validate() error {
	return nil
}

Validate starts empty; fill it in as Rails's validates would. It runs on both create and update, inside the store, so every caller gets it and none can forget it.

The store

app/models/posts.go converts between the domain type and sqlc's row type, maps "no rows" to domain.ErrNotFound, and runs Validate before writing:

func (s *Store) CreatePost(ctx context.Context, p domain.Post) (domain.Post, error) {
	if err := p.Validate(); err != nil {
		return domain.Post{}, err
	}
	row, err := s.q.CreatePost(ctx, CreatePostParams{Title: p.Title, Body: p.Body})
	if err != nil {
		return domain.Post{}, fmt.Errorf("models: create post: %w", err)
	}
	return postFromRow(row), nil
}

GetPost, ListPosts, UpdatePost and DeletePost follow the same shape. app/models/posts_test.go is a Ginkgo spec on the real test database: an unknown or malformed id is ErrNotFound, an update to a missing post is ErrNotFound, and a saved post reads back, lists, updates and deletes. test/factories/posts.go builds valid posts for it and for every other spec (factories.Post(GinkgoT(), store)). It's yours to edit once written. Store specs need the database up: make up first. See Testing and CI.

Attribute types

string text integer bigint boolean datetime uuid jsonb references, each optionally followed by :index or :uniq:

bogie g model comment body:text post:references score:integer

string is Postgres varchar (unlimited, as Rails leaves it with no :limit) and text is text: the distinction Rails makes is kept, not collapsed. Columns written by v0.2.3 and earlier keep whatever their migration already says.

post:references writes the column post_id as bigint NOT NULL REFERENCES posts (id), with its own index (uuid in an --id=uuid app: a foreign key is always made of whatever its target's id is). slug:string:uniq adds a unique constraint.

Id schemes

Since v0.2.9 every id is a bigserial, an auto-incrementing bigint, as Rails does by default. bogie new NAME --id=uuid makes them uuid PRIMARY KEY DEFAULT gen_random_uuid() instead. Pick uuid when an API should not reveal how many records exist (/orders/41 next to /orders/42 does); pick bigint when people read the ids.

bogie new blog              # id bigserial, domain ID int64
bogie new blog --id=uuid    # id uuid, domain ID string

The choice is made once, for the whole app, and written to bogie.toml as id = "bigint" or id = "uuid". Every later g model, g scaffold and g authentication reads it, and so does app:update. It cannot be mixed per model, because a references column has to match the id it points to. Store methods still take the id as the string from the URL; the store parses it for its scheme, and an id that does not parse is ErrNotFound.

An app made before v0.2.9 has no id line in bogie.toml. That reads as uuid, what it was always generated with, so its new models keep matching its old tables. Do not add id = "bigint" to such an app: new tables would get bigint ids and the new references columns would no longer match the uuid ids already there.

Changing a table

bogie g migration add_slug_to_posts slug:string:uniq
bogie g migration remove_draft_from_posts draft:boolean

Three migration name shapes get their SQL written automatically; any other name gets an empty Up and Down to fill in by hand:

  • create_<table>: the table and its columns.
  • add_<x>_to_<table>: ALTER TABLE ... ADD COLUMN for each attribute, reversed on the way down.
  • remove_<x>_from_<table>: ALTER TABLE ... DROP COLUMN, with the Down able to re-add it.
-- +goose Up
ALTER TABLE posts ADD COLUMN slug varchar NOT NULL DEFAULT '' UNIQUE;

-- +goose Down
ALTER TABLE posts DROP COLUMN slug;

The migration generator runs sqlc immediately too, so app/models/*.sql.go changes before the migration is ever applied, and a renamed column shows up as a compile error right away.

Running them

bogie db:migrate
bogie db:rollback
bogie db:migrate:status
bogie db:reset
bogie db:seed
bogie db:version

All through the app's own binary, never the goose CLI directly, so development runs exactly what a deployed container runs. db:reset drops the database and rebuilds it from the migrations; there is no schema.rb to load instead. Seeds are not migrations: they are plain Go, written with bogie g seed and run, every one of them, by bogie db:seed. See Seeds.

Hand-written code beside generated code

g model writes two files whole every time it runs: db/queries/<table>.sql and app/models/<table>.go. A query or method written straight into either is reported conflict on the next run. Since v0.2.10 both files open with a comment that says so. Put your own code in a sibling _extra file instead:

  • db/queries/posts_extra.sql for a hand-written query. sqlc compiles every *.sql file in db/queries/, so make sqlc picks it up like the generated ones.
  • app/models/posts_extra.go for a hand-written store method. Go merges every file in a package, so the store gains the method and the generator never sees it.
-- db/queries/posts_extra.sql
-- name: ListPostsByTitle :many
SELECT * FROM posts WHERE title = $1 ORDER BY created_at DESC;
// app/models/posts_extra.go
package models

func (s *Store) PostsByTitle(ctx context.Context, title string) ([]domain.Post, error) {
	// call s.q.ListPostsByTitle (written by make sqlc) and convert
	// each row with postFromRow, as the generated methods do
}

Taking it out

bogie d model post

Removes the migration, the queries, the domain type and the store, the same way bogie g model wrote them.
