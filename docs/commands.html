Command reference

Tasks use a colon (db:migrate); the rest are plain words. bogie help prints the authoritative short version of this page from inside an app.

Bogie, outside an app

CommandDoes
bogie new NAME [--module=PATH] [--id=bigint|uuid] [--jobs]Generates a new service in ./NAME. --id picks the primary key scheme for the whole app: bigint, the default, or uuid. See Id schemes.
bogie versionPrints the version.
bogie helpThis text.

Bogie, inside an app

Found by its bogie.toml, from any subdirectory.

CommandDoes
bogie generate GENERATOR NAME, bogie gRuns a generator: scaffold, scaffold_controller, model, migration, controller, service, job, seed, config, authentication. bogie g -h for its own usage, inside an app.
bogie destroy GENERATOR NAME, bogie dRemoves what a generator made, registration included.
bogie doctorChecks markers, pinned tools and layout files; confirms every controller is constructed and mounted.
bogie model:sync [TABLE]Brings a model in line with the schema after a migration, generated or hand-written: adds the field for each new column, removes the field for each column a migration dropped, and merges the regenerated queries, store and factory into your copies. Validate, the views, the controllers and the specs stay yours. Without TABLE it syncs every model. Refuses on a dirty git tree. See Models and migrations.
bogie app:update [--pretend]Moves the app to the installed Bogie's layout: a three-way merge between what the recorded version generated, what this version generates, and the file on disk. Refuses on a dirty git tree; a real overlap leaves conflict markers.
bogie server, bogie sRuns the app; migrates at boot. In development it runs under Air: save a file and it rebuilds and restarts.
bogie workerWorks the job queue (apps with jobs; g job adds them to one that has none). Reloads under Air in development, same as bogie server, to its own binary so the two can run side by side.
bogie routesEvery mounted route, method, path and handler. It boots the app the way serve does, so the list is what is actually wired. Prints in development only; in test or production it exits 0 with no output.
bogie test [PKGS], bogie tgo test -p 1 -race -cover ./...: Ginkgo specs, one package at a time.
bogie lintgofmt check, go vet, golangci-lint.
bogie ciEvery check, locally, then sign off: bin/ci.
bogie db:createCreates the database for the current environment.
bogie db:dropDrops it, with --yes added for you.
bogie db:prepare (db:setup)Create, migrate, seed.
bogie db:resetDrop then prepare.
bogie db:migrateApplies pending migrations.
bogie db:migrate:statusWhich migrations have run, which are pending.
bogie db:migrate:redoRolls the last migration back and re-applies it.
bogie db:rollbackRolls back the most recent migration.
bogie db:versionThe current schema version.
bogie db:seedRuns every seed in db/seeds, every time, in registration order; each must be safe to run twice.
bogie credentials:edit [-e ENV]Opens the encrypted settings for editing.
bogie credentials:show [-e ENV]Prints the decrypted file.
bogie credentials:get [-e ENV] KEYPrints one value.

Tasks that destroy pass --yes on your behalf here, the way a laptop command should; the app's own binary in a deployed container keeps asking. bogie db:migrate:up or any other near-miss points at the nearest real task rather than printing the whole usage.

The reload under bogie server and bogie worker is development only: set <NAME>_ENV to anything else and the plain compiled binary runs with no watcher. Air is pinned as a go tool dependency in the app's own go.mod, next to goose, sqlc and credentials, so a fresh clone needs only Go. Its settings are .air.toml; deleting that file turns reload off.

Generators: bogie g / bogie d

GeneratorArgumentsWrites
migrationNAME [field:type ...]db/migrate/<stamp>_NAME.sql. create_<table>, add_<x>_to_<table> and remove_<x>_from_<table> write their SQL.
modelNAME [field:type ...]The migration, db/queries/<table>.sql, app/models/<name>.go and the store's db/adapter/<table>.go, their two specs and a factory; then runs sqlc into db/sqlc.
scaffoldNAME [field:type ...]The model, plus app/views/<table>.go and a <Table>Controller with real handlers over the store, registered. The model is singular, the rest plural. --only index,show writes just those actions, with their routes, views and specs (the model half is always whole). admin/NAME is a model of its own, admin_page with table admin_pages, whose PagesController answers at /admin/pages.
scaffold_controller[NS/]RESOURCEThe HTTP half of a scaffold, for a model that already exists: admin/categories mounts the five actions over the category store under /admin/categories, reading the attributes from app/models. A namespaced one writes views of its own, app/views/admin_categories.go. --only works here too.
controllerNAME [action ...]app/controllers/<name>_controller.go, one controller in one file, registered: a field, a wire line and a mount above each marker. Name a resource in the plural. admin/NAME puts it in the admin namespace, app/controllers/admin_controllers/, made on first use and registered the same way.
serviceNAMEapp/services/<name>/, ctx first, no HTTP, not wired anywhere.
jobNAMEapp/jobs/<name>.go, a River job, registered above bogie:jobs; the first one on an app with no jobs adds them first, merged in like app:update.
seedNAMEdb/seeds/<name>.go, registered above bogie:seeds in db/seeds/seeds.go. Unlike a migration, db seed runs every seed every time: write it safe to run twice.
config[GROUP] key[:type][:flag][=value] ...A typed group of the credentials file in config/<group>.go, registered, with development values; or keys into an existing group (server, database); or, with no group, flat top-level keys. See Configuration.
authenticationSHAPEA middleware on a route group, its config key with a development value written to the credentials, and a WithX group helper on the root Server. SHAPE is secret (a trusted service calls this one), token (bearer JWT a user presents) or api_key (keys for machine clients, with a table and api_keys:create).

Flags: --pretend reports without writing (even g job on an app with no jobs, which only says --jobs would be added first), --force overwrites a file that differs, --only ACTIONS limits a scaffold to the actions listed, --skip-sqlc skips the sqlc run. Run a generator again and each file is reported identical, or conflict if it differs from what the generator would write; only --force overwrites. Attributes are field:type, with :index or :uniq after the type: string text integer bigint boolean datetime uuid jsonb references. A field with no :type defaults to string. A references field names the other model: post:references is post_id. :null follows a type for a column that may be NULL (archived_at:datetime:null).

bogie d GENERATOR NAME removes what the generator of the same name created: its files, and for a controller the three lines that registered it. bogie d scaffold_controller admin/categories removes just the controller half. A namespaced controller's package goes too once it holds no controller; bogie d authentication token also removes its config group, leaving the development value harmless in the credentials file.

api_key registers a subcommand on the app's own binary, not on bogie: bogie api_keys:create NAME reaches it through the same proxy rule as db:*, any colon task bogie does not know itself is shorthand for the binary's own, so it runs blog api_keys create NAME.

The app binary itself

A plain Go CLI with spaces, the form bogie accepts too (bogie db prepare works from outside, since the colon tasks above are shorthand for exactly these):

CommandDoes
blog serveRuns the HTTP server.
blog workerWorks the job queue (apps with jobs enabled).
blog db createCreates the database this environment points at.
blog db drop --yesDrops it; refused in production.
blog db prepareCreate if needed, migrate, seed.
blog db seedRuns every seed in db/seeds; each one runs again every time.
blog routesEvery mounted route (development only).
blog migrate statusWhich migrations have run, which are pending.
blog migrate versionThe current schema version.
blog migrate upApplies every pending migration (also done at boot).
blog migrate down --yesRolls back the most recent migration.
blog migrate down-to N --yesRolls back until the schema is at version N (0 = empty).

These run against whatever database the current <NAME>_ENV selects, including on a deployed host: docker exec <container> blog migrate status.
