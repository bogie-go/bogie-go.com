Background jobs

Jobs are opt-in, added when the app is generated:

bogie new blog --jobs

This runs River on the same Postgres the app already has: no Redis, a transactional enqueue, typed args. It adds a worker role, app/jobs, and g job. An app made without --jobs refuses the generator with a clear error:

bogie: generate job: this app has no app/jobs; it was generated without --jobs (AGENTS.md says what --jobs adds, if you want to add it by hand)

Writing one

bogie g job send_welcome
      create  app/jobs/send_welcome.go
      create  app/jobs/send_welcome_test.go
      insert  app/jobs/jobs.go: registered += add(workers, &SendWelcomeWorker{Log: log})
type SendWelcomeArgs struct {
	// ID string `json:"id"`
}

func (SendWelcomeArgs) Kind() string { return "send_welcome" }

type SendWelcomeWorker struct {
	river.WorkerDefaults[SendWelcomeArgs]
	Log *slog.Logger
}

func (w *SendWelcomeWorker) Work(ctx context.Context, job *river.Job[SendWelcomeArgs]) error {
	w.Log.InfoContext(ctx, "send_welcome: not implemented yet", "job", job.ID)
	return nil
}

An Args type with a Kind, and a Worker with Work(ctx, job). Args are stored as JSON in the job row, so keep them to ids and small values; the worker loads whatever else it needs. Never change Kind once jobs of it have been queued: a queued job of the old kind would have no worker to run it. Dependencies go on the worker as fields, the smallest interface it needs (rule 2), passed on the registration line.

The marker

The generator registers the worker above // bogie:jobs in app/jobs/jobs.go, the same idempotent, checked-before-written insertion every generator uses:

registered += add(workers, &SendWelcomeWorker{Log: log})
// bogie:jobs

Enqueuing

From anywhere that holds the application, including inside a transaction so the job commits with the row it depends on or not at all:

app.Jobs.Insert(ctx, jobs.SendWelcomeArgs{}, nil)

// or, so the enqueue commits with the row:
app.Jobs.InsertTx(ctx, tx, jobs.SendWelcomeArgs{}, nil)

Running the worker

bogie worker

Or make worker. It is its own process, separate from bogie server, so a backlog in the queue never slows a request. River's own schema (the tables it needs to track jobs) is applied by migrate, through rivermigrate, not copied into db/migrate: it arrives the same way the app's own migrations do, at boot or with bogie db:migrate.

Removing one

bogie d job send_welcome

Removes the file and the registration line.
