Upgrading an app

The generated app never imports Bogie, so a new Bogie release changes nothing in an app until you ask. bogie app:update is the asking: rails app:update, done as a three-way merge.

Upgrade

go install github.com/bogie-go/bogie@latest   # {{VERSION}} as of this build
cd blog
git commit -am "before app:update"            # it refuses a dirty tree
bogie app:update --pretend                    # the report only; nothing written
bogie app:update

How the merge works

bogie.toml records the Bogie version that generated the app. app:update renders what that version generated (the base), renders what the installed version generates (theirs), and merges each template-owned file on disk (ours, with your edits) using git merge-file:

  • A file you never touched updates silently.
  • A file you edited where the template did not change merges cleanly.
  • Only a real overlap leaves conflict markers, and the report names those files.
  • A file the new version no longer generates is reported retired and left as it is; delete it yourself once nothing uses it.

Files the templates never produced, everything bogie g and you wrote, are not touched. Afterwards bogie.toml records the new version, go mod tidy runs, and bogie doctor checks the markers. Because the tree was clean, the whole upgrade is one reviewable diff.

What it does not carry

Only files the tool templates into an app. A change inside Bogie itself, such as v0.2.4's string now being varchar, affects what generators write from then on and leaves existing migrations alone. A change in shape, such as v0.2.6's move from SQL seeds to Go seeds, brings in the new layout but does not translate content: port old seeds by hand first. Each release note says which kind it is.

One setting is never changed for you: the id scheme. An app made before v0.2.9 has no id line in bogie.toml, and app:update reads that as uuid, so the app keeps uuid ids after upgrading. See Id schemes.

Moving an app from v0.2 to v0.3

v0.3.0 changed two things app:update cannot do for you, because the files involved are yours: the encrypted credentials and the variables you set in your shell, CI and deploy config. Until you move them, the app still builds and boots, and quietly ignores the old settings: a key left in the old flat section is never read, and an old BLOG_DATABASE_URL is not a variable anything reads any more, so development falls back to the bundled database on :5440 and production refuses to start for lack of a URL.

  1. Rename the variables, in your shell, CI and deploy config (blog stands for your app's name):
    v0.2v0.3
    BLOG_DATABASE_URLDATABASE_URL
    BLOG_MIGRATE_AT_BOOTDATABASE_MIGRATE_AT_BOOT
    BLOG_ADDRSERVER_ADDR
    BLOG_LOG_LEVELSERVER_LOG_LEVEL
    BLOG_SHUTDOWN_GRACESERVER_SHUTDOWN_GRACE
    BLOG_ENV, BLOG_CREDENTIALS, BLOG_MASTER_KEY, BLOG_CONFIG_DIR and BLOG_TEST_DATABASE_URL keep the app's name.
  2. Restructure each credentials file (bogie credentials:edit, and -e production for the others) from the flat section named after the app into groups: 
    # v0.2                              # v0.3
blog:                               server:
  addr: ":8080"                       addr: ":8080"
  log_level: debug                    log_level: debug
  database_url: postgres://...      database:
                                      url: postgres://...
    bogie credentials:get database.url reads one key back, and bogie g config adds your own keys from here on.
  3. If go build then says undefined: credentials.ApplyEnvOverrides, the app still pins the old credentials module (v0.3.2 and earlier did not raise it). Run go get github.com/bogie-go/credentials@v1.6.0 and commit the result.

The release notes list every rename; Configuration describes the new layout.

Moving an app from v0.3 to v0.4

v0.4.0 and v0.4.1 change how a generated app tests: a test/ folder for what tests share, and Ginkgo and Gomega specs in every package. There's nothing to rename and no settings move, so app:update does most of it. Commit, then run bogie app:update --pretend to see the plan, then bogie app:update. It:

  • Adds a <pkg>_suite_test.go in app/controllers, app/models, app/middlewares, app/services/database and config, the export_test.go files, and the whole test/ tree (testdb, testapp, factories, requests).
  • Updates the scaffold's own tests (routes_test.go, config_test.go, database_test.go) to Ginkgo, plus bin/ci, the Makefile, .golangci.yml and AGENTS.md. go test becomes go test -p 1, because the packages share one test database.
  • Runs go mod tidy, which adds github.com/onsi/ginkgo/v2 and github.com/onsi/gomega to go.mod and go.sum.

What it leaves for you:

  1. Tests generators wrote earlier stay as they are. A posts_test.go or posts_controller_test.go from v0.3 is stdlib testing in the package itself, and it keeps running next to the new suites. To move a resource to specs, re-run its generator (bogie g scaffold post title:string body:text, or g model), which rewrites its tests and writes its factory. Port any tests you added by hand to those files first, or keep them in a file of your own.
  2. app/models/store_test.go is reported retired and left in place, because the old model tests call its testStore. Delete it once none of them does. The replacement is testdb.Store.
  3. Run bin/ci. A fresh v0.3.2 app with one scaffold came through app:update to v0.4.1 with no conflicts, and its bin/ci passed, old tests and new specs together.

An app still on v0.2 should make the v0.3 move above first. Its store_test.go reads the old flat config, so after updating to v0.4 it no longer compiles: delete it and move its model tests to the new specs. Testing and CI describes the new layout.

Moving an app from v0.4 to v0.5

v0.5.0 moved the layers of a generated app, and app:update merges one file at a time, so it cannot follow a move. Run on an app made by v0.4.1 or earlier, it exits with a conflict and the app no longer builds. What moved:

v0.4v0.5
app/domain/ (the types and their rules)app/models/
app/models/ (the Store, ids, uuid.go)db/adapter/
sqlc's output in app/models/db/sqlc/

The conflict is in app/models/models.go: in v0.4 that file is sqlc's generated output, and in v0.5 the same path holds the package doc and the ErrNotFound and ErrInvalid errors. The old files are reported retired and left in place, so the old and new layers sit side by side until you remove the old ones.

These steps worked on a v0.4.1 app with one scaffold, both a default (bigint) app and one made with --id=uuid, and bin/ci passed on both. A v0.2 or v0.3 app should make the v0.3 and v0.4 moves above first.

  1. Commit (git commit -am "before app:update"), install the new Bogie, and run bogie app:update. It exits 1 with conflict app/models/models.go. That is expected; the other files are updated.
  2. In app/models/models.go, keep the bogie v0.5 side of the conflict (the package doc and the two errors) and delete the yours side and the markers.
  3. Delete the old layout. For each model, that is its app/models/<table>.go, <table>.sql.go and <table>_test.go: 
    rm -rf app/domain
rm app/models/db.go app/models/id.go app/models/store.go
rm app/models/products.go app/models/products.sql.go app/models/products_test.go
rm -f app/models/uuid.go   # uuid apps only; app:update does not list it as retired
    A uuid app that keeps uuid.go fails golangci-lint with parseUUID is unused.
  4. Regenerate each resource into the new layout. --force rewrites its files; the migration is reported identical, so no second one is written: 
    bogie g scaffold product name:string price:integer --force
    For a model without a controller, use g model with the same attributes and --force. It writes app/models/<name>.go and db/adapter/<table>.go, with the factory, controller and specs, and runs sqlc into db/sqlc.
  5. Run go build ./..., bogie doctor and bin/ci, then commit.

Know before you start. Regenerating overwrites the files it writes, so port any hand edits in your store, controller, views or specs into the new files afterwards. Only apps with scaffolds were tried. Apps with hand-written store code, g authentication, g config, jobs or services were not, so check those by hand.
