Bogie
Guides From Rails Commands Design Source

The Go service next to your Rails app.

A CLI that scaffolds an API-only, Postgres-only Go service out of tools the Go ecosystem already ships, with rails new-style generators that also wire the code in. The generated app never imports Bogie.

Get started Read the guides

Pre-release 
go install github.com/bogie-go/bogie@latest
bogie new blog
cd blog && bogie db:prepare && bogie server

Why it exists

Every Rails shop eventually needs one service that Rails is the wrong tool for: a webhook receiver that must answer in under a second while a platform retries at it, a socket gateway holding thousands of idle connections, a worker draining a queue against a rate-limited API. The web app stays in Rails. That one thing goes to Go, and the first attempt usually goes badly, not because of Go but because everything Rails decided for you is suddenly yours to decide.

A bogie is the wheeled frame under a rail car that carries it along the track. The car body, your application code, is yours.

What it is, and is not

Glue, then gaps

For every Rails concept, the ecosystem tool, wired once: Gin, sqlc with pgx, goose, River, Kamal. Only what has no equivalent gets built.

Not a framework

No bogie.Application, no base classes, no DSL. Bogie renders templates and shells out. Delete the tool tomorrow and the app does not notice.

Rails spelling, Rails layout

db:migrate, credentials:edit, g controller, app/controllers, db/migrate. Everything is where a Rails developer would look for it.

Generators that wire

Go has no autoload. bogie g controller posts index show writes the controller and registers it in the three places it must be, above marker comments, idempotently. bogie d takes it out again.

Written for agents as much as people

The generated app ships an AGENTS.md with the rules, the commands and a recipe per task. An agent that runs the generators gets the registration right every time.

CI on your machine

bin/ci is the whole pipeline, as in Rails 8.1, and a green run signs off the commit. The generated app ships one too. No hosted runner, no telemetry.

Everything you need

Models keep the SQL honest

bogie g model post title:string body:text writes a domain type that imports nothing third-party, a store that converts it to and from a row, and a named query.

sqlc compiles that query against the migrations at generation time. Misspell a column and it fails at make sqlc, not in production.

Controllers convert and call

A handler converts HTTP into domain values, calls one method on a store interface declared next to it holding only what that controller needs, and converts the result back.

*gin.Context never travels below app/controllers (rule 5), so everything it calls can be tested or reused without one.

Resources, controllers and routing →

type postsStore interface {
	CreatePost(ctx context.Context, p domain.Post) (domain.Post, error)
	GetPost(ctx context.Context, id string) (domain.Post, error)
	ListPosts(ctx context.Context, limit int32) ([]domain.Post, error)
	UpdatePost(ctx context.Context, p domain.Post) (domain.Post, error)
	DeletePost(ctx context.Context, id string) error
}

func (ctl *PostsController) SetupRoutes(router *gin.RouterGroup) {
	posts := router.Group("/posts")
	posts.GET("", ctl.Index)
	posts.POST("", ctl.Create)
	posts.GET("/:id", ctl.Show)
	posts.PATCH("/:id", ctl.Update)
	posts.DELETE("/:id", ctl.Destroy)
}

func (ctl *PostsController) Index(c *gin.Context) {
	posts, err := ctl.Store.ListPosts(c.Request.Context(), postsListLimit)
	if err != nil {
		ctl.fail(c, err)
		return
	}
	c.JSON(http.StatusOK, postsView(posts))
}

Views are the wire contract

app/views/posts.go holds PostRequest and PostResponse. A domain type never doubles as a wire type, so a field added to the database does not silently appear on the wire.

Views: wire structs, never the domain type →

type PostRequest struct {
	Title       string    `json:"title"`
	Body        string    `json:"body"`
	Score       int32     `json:"score"`
	PublishedAt time.Time `json:"published_at"`
	AuthorID    string    `json:"author_id"`
}

type PostResponse struct {
	ID          string    `json:"id"`
	Title       string    `json:"title"`
	Body        string    `json:"body"`
	Score       int32     `json:"score"`
	PublishedAt time.Time `json:"published_at"`
	AuthorID    string    `json:"author_id"`
	CreatedAt   time.Time `json:"created_at"`
	UpdatedAt   time.Time `json:"updated_at"`
}

Routes are one file, registered by the generator

Go has no autoload: a controller that compiles but is never mounted serves nothing. bogie g controller inserts these three lines above three bogie: markers, idempotently; bogie d removes them again.

Jobs commit with the row

River runs on the same Postgres as the app: no Redis, no second system to keep up. Enqueue inside the transaction that created the row with InsertTx, and the job commits with it or not at all.

Background jobs →

type SendWelcomeArgs struct{}

func (SendWelcomeArgs) Kind() string { return "send_welcome" }

type SendWelcomeWorker struct {
	river.WorkerDefaults[SendWelcomeArgs]
	Log *slog.Logger
}

func (w *SendWelcomeWorker) Work(ctx context.Context, job *river.Job[SendWelcomeArgs]) error {
	w.Log.InfoContext(ctx, "send_welcome: not implemented yet", "job", job.ID)
	return nil
}

Optimized for the Rails developer

The generated app ships an AGENTS.md (CLAUDE.md included) holding these six rules, every command, and a recipe per generator, so the registration is right whether the hand on the keyboard is a person's or an agent's.

  1. ctx context.Context is the first parameter of anything doing I/O.
  2. Interfaces are declared where they are consumed, holding only the methods used there.
  3. app/domain imports nothing third-party.
  4. Constructors return (T, error). Only main exits.
  5. *gin.Context never travels below app/controllers.
  6. No util/, helpers/ or common/.
