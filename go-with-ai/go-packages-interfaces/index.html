Chapter 5: Organizing Code: Packages and Interfaces

In short: Chapter 5 splits Tracker into packages and introduces interfaces, with one Storage interface that has a file version and an in-memory version for tests. The behavior doesn't change, so your tests make the refactor safe, and the AI starts implementing code to your rules.

Look at Tracker’s folder. Formatting money, storing expenses, reading the command line and printing the report all live in package main. It works, but it’s getting crowded, and a crowded package is hard to read, for you and for the AI. When everything can touch everything, every change is risky.

In this chapter, you’ll split Tracker into packages: one for money, one for expenses. You’ll decide what each package shows to the outside world with exported names. And you’ll give Tracker an interface for storage, so the same code can save to a file in real use and keep everything in memory during tests.

The AI’s role changes twice in this chapter. First it’s your pair: you do the reorganizing, and it reviews. Then, for the first time, it’s the implementer: you write the tests, the AI writes the code, and you review it. It’s the same SURE loop, but by the end of this chapter the AI is typing and you’re the one deciding whether its work is good enough.

Mission

By the end of this chapter, you’ll have:

  • A money package that formats amounts, and a ledger package that records and stores expenses
  • A Storage interface, with a file version for the program and a memory version for tests
  • One set of tests that every kind of storage must pass
  • Your expenses kept out of Git with a .gitignore file
  • Two commits: one for your reorganization, one for the AI’s code

Tracker’s behavior won’t change at all. Every command from Chapter 4 prints exactly what it did before. Changing how code is organized without changing what it does is called refactoring, and your tests are what make it safe.

Must know

  1. A package is a folder. Every .go file in a folder starts with the same package line. Other code imports it by your module’s name plus the folder: "tracker/ledger".
  2. A capital first letter means exported. money.Format can be used from other packages; money.splitCents can’t. The rule is the same for functions, types, methods and struct fields.
  3. Name things for how they read from outside. Callers write money.Format(350) and ledger.Open(...), so don’t repeat the package name: money.FormatMoney says “money” twice.
  4. An interface is a list of methods. Any type that has all those methods satisfies the interface automatically. Go has no implements keyword.
  5. Pointer receivers count. If a type’s methods have pointer receivers, like (m *MemoryStorage), then only the pointer, &MemoryStorage{}, satisfies the interface.

        {Category: "Food", Cents: 350},
        {Category: "Transport", Cents: 1200},

    got := tr.Totals()

func TestOpenAddSave(t *testing.T) {

    first, err := Open(store)
    if err != nil {
        t.Fatalf("Open() error = %v", err)
    }
    if err := first.Add("Food", 350); err != nil {
        t.Fatalf("Add() error = %v", err)
    }
    if err := first.Save(); err != nil {
        t.Fatalf("Save() error = %v", err)

        t.Errorf("Totals() after reopening = %v, want %v", got, want)

}

TestOpenAddSave uses MemoryStorage, so it never touches the disk. That’s the first payoff of an interface: Tracker doesn’t care where its expenses go.

Also in ledger, create storage_test.go. This is the heart of the chapter:

package ledger

import (
    "os"
    "path/filepath"
    "slices"
    "testing"
)

// testStorage checks the rules every Storage must follow.
func testStorage(t *testing.T, store Storage) {
    t.Helper()

    saved := []Expense{
        {Category: "Food", Cents: 350},
        {Category: "Fun", Cents: 1500},
    }
    if err := store.Save(saved); err != nil {
        t.Fatalf("Save() error = %v", err)
    }
    saved[0].Cents = 1 // Changing our slice must not change what was saved.

    got, err := store.Load()
    if err != nil {
        t.Fatalf("Load() error = %v", err)
    }
    want := []Expense{
        {Category: "Food", Cents: 350},
        {Category: "Fun", Cents: 1500},
    }
    if !slices.Equal(got, want) {
        t.Errorf("Load() = %v, want %v", got, want)
    }
}

func TestFileStorage(t *testing.T) {
    path := filepath.Join(t.TempDir(), "expenses.json")
    testStorage(t, FileStorage{Path: path})
}

func TestFileStorageMissingFile(t *testing.T) {
    path := filepath.Join(t.TempDir(), "missing.json")
    store := FileStorage{Path: path}
    got, err := store.Load()
    if err != nil {
        t.Fatalf("Load() error = %v, want nil", err)
    }
    if len(got) != 0 {
        t.Errorf("Load() returned %d expenses, want 0", len(got))
    }
}

func TestFileStorageBrokenFile(t *testing.T) {
    path := filepath.Join(t.TempDir(), "expenses.json")
    if err := os.WriteFile(path, []byte("not json"), 0o644); err != nil {
        t.Fatal(err)
    }
    store := FileStorage{Path: path}
    if _, err := store.Load(); err == nil {
        t.Error("Load() error = nil, want an error for a broken file")
    }
}

func TestMemoryStorage(t *testing.T) {
    testStorage(t, &MemoryStorage{})
}

testStorage isn’t a test by itself; its name doesn’t start with Test. It’s a helper that takes any Storage and checks the rules every storage must follow. TestFileStorage and TestMemoryStorage each run it on one kind of storage. Write the rules once, check every version.

Look at the line saved[0].Cents = 1. After saving, the test changes its own slice, and then checks that the storage still returns the original amounts. A file naturally keeps its own copy. The memory version must do the same on purpose, and this line checks that it does.

t.Helper() tells Go that this is a helper, so when it fails, Go reports the line in the test that called it, not a line inside the helper.

The money package

Create money/money.go. Move formatAmount and splitCents into it from main.go, rename formatAmount to Format (capital F, so other packages can use it), and add comments. It should look like this:

// Package money formats amounts stored as whole cents.
package money

import "fmt"

// Format returns an amount in cents as text, like "3.50".
func Format(cents int) string {
    whole, rest := splitCents(cents)
    return fmt.Sprintf("%d.%02d", whole, rest)
}

func splitCents(cents int) (int, int) {
    return cents / 100, cents % 100
}

splitCents stays lowercase. Nothing outside money needs it, so it stays private, and you can change it later without breaking anyone.

A comment that starts with the name it describes, like // Format returns..., is a doc comment. Go’s tools show it to anyone who uses the package.

The ledger package

Create ledger/ledger.go. Move Expense, ErrInvalidAmount, Tracker, Add and Totals into it from tracker.go. Two things change:

  • Tracker gets a second field, store Storage, so it knows where its expenses are saved.
  • Instead of Load(path), there’s Open(store), which loads expenses from any Storage. Save loses its path parameter, because the Tracker already knows its store.
// Package ledger records expenses and totals them by category.
package ledger

import (
    "errors"
    "fmt"
)

// Expense is one thing you spent money on.
type Expense struct {
    Category string `json:"category"`
    Cents    int    `json:"cents"`
}

// ErrInvalidAmount means an expense amount was zero or negative.
var ErrInvalidAmount = errors.New("amount must be more than zero")

// Tracker holds all your expenses and the storage they live in.
type Tracker struct {
    store    Storage
    expenses []Expense
}

// Open loads the expenses from store into a new Tracker.
func Open(store Storage) (*Tracker, error) {
    expenses, err := store.Load()
    if err != nil {
        return nil, err
    }
    return &Tracker{store: store, expenses: expenses}, nil
}

// Add records one expense.
func (tr *Tracker) Add(category string, cents int) error {
    if cents <= 0 {
        return fmt.Errorf("add %q: %w", category, ErrInvalidAmount)
    }
    tr.expenses = append(tr.expenses, Expense{Category: category, Cents: cents})
    return nil
}

// Totals returns the total in cents for each category.
func (tr *Tracker) Totals() map[string]int {
    totals := make(map[string]int)
    for _, e := range tr.expenses {
        totals[e.Category] += e.Cents
    }
    return totals
}

// Save writes all expenses to the Tracker's storage.
func (tr *Tracker) Save() error {
    return tr.store.Save(tr.expenses)
}

Now create ledger/storage.go, with the Storage interface and the file version. FileStorage’s two methods are your old Load and Save, reshaped to fit the interface:

package ledger

import (
    "encoding/json"
    "errors"
    "fmt"
    "os"
)

// Storage saves and loads expenses.
type Storage interface {
    Load() ([]Expense, error)
    Save(expenses []Expense) error
}

// FileStorage keeps expenses in a JSON file.
type FileStorage struct {
    Path string
}

// Load reads expenses from the file. A missing file means no expenses yet.
func (s FileStorage) Load() ([]Expense, error) {
    data, err := os.ReadFile(s.Path)
    if errors.Is(err, os.ErrNotExist) {
        return nil, nil
    }
    if err != nil {
        return nil, fmt.Errorf("load expenses: %w", err)
    }
    var expenses []Expense
    if err := json.Unmarshal(data, &expenses); err != nil {
        return nil, fmt.Errorf("load expenses: %w", err)
    }
    return expenses, nil
}

// Save writes expenses to the file as JSON.
func (s FileStorage) Save(expenses []Expense) error {
    data, err := json.MarshalIndent(expenses, "", "  ")
    if err != nil {
        return fmt.Errorf("save expenses: %w", err)
    }
    if err := os.WriteFile(s.Path, data, 0o644); err != nil {
        return fmt.Errorf("save expenses: %w", err)
    }
    return nil
}

The interface says what storage can do: Load and Save. FileStorage says how. Nowhere does FileStorage mention Storage. It has both methods, so it satisfies the interface, and that’s all Go needs.

FileStorage’s methods use a value receiver, (s FileStorage), because they never change s. They only read s.Path.

Keep personal data out of Git

Since storage moved, now’s the time to fix something from Chapter 4: expenses.json is in Git. Your expenses are made up, but real ones are personal. And once something is committed, it stays in your project’s history even after you delete the file. If you ever push the project online, everyone can read that history. The safest data is data that never enters Git.

Create a file named .gitignore in the tracker folder with one line:

expenses.json

Make sure the file is named exactly .gitignore, with no .txt at the end. (Notepad on Windows likes to add one.) .gitignore tells Git which files to leave alone. But it only affects files Git isn’t already tracking, and Git has tracked expenses.json since Chapter 4. So tell Git to stop, without deleting your file:

git rm --cached expenses.json
rm 'expenses.json'

--cached means “remove it from Git, but keep it on disk.” Your expenses are still there; run go run . to check.

Review the AI’s work

As the implementer’s reviewer, check in this order:

  1. Did it touch only what you asked?

    git status --short
     M ledger/storage.go

    One changed file. If a test file appears here, the AI changed your tests. Undo that with git restore and the file’s name, and ask again.

  2. Let Go check. gofmt -l . and go vet ./... print nothing, and go test ./... prints ok three times.

  3. Read the change. git diff shows exactly which lines the AI added. Read every one. Can you explain each line? Why does it need a pointer receiver? How does it keep its own copy?

Here’s one version that passes. The AI’s may look different:

// MemoryStorage keeps expenses in memory. Nothing is written to disk.
type MemoryStorage struct {
    expenses []Expense
}

// Load returns a copy of the saved expenses.
func (m *MemoryStorage) Load() ([]Expense, error) {
    return slices.Clone(m.expenses), nil
}

// Save keeps a copy of expenses.
func (m *MemoryStorage) Save(expenses []Expense) error {
    m.expenses = slices.Clone(expenses)
    return nil
}

This version also adds "slices" to the imports in storage.go. Save needs a pointer receiver because it changes m.expenses; that’s Chapter 4’s lesson again. slices.Clone makes a copy, so changing the caller’s slice can’t change what was saved. That’s what the saved[0].Cents = 1 line in your test checks.

Where AI gets Go wrong: packages and interfaces

  • Changing tests to make them pass. When asked to “make the tests pass,” an AI may edit the tests instead of the code. Always check git status after an implementer task.
  • Vague package names. utils, common, helpers and models say nothing about what’s inside, and they grow into junk drawers. Name a package for what it provides.
  • Stutter. money.FormatMoney or ledger.LedgerTracker repeats the package name. Callers already see it.
  • Interfaces for everything. AI often creates an interface for every type “just in case.” Make one when you have two real versions, as with Storage, and keep it as small as its users need.
  • Value instead of pointer. If TestMemoryStorage used MemoryStorage{} instead of &MemoryStorage{}, the test wouldn’t compile: MemoryStorage does not implement Storage (method Load has pointer receiver). The fix is the &, not changing the receivers.
