Every chapter’s Review checklist and “Where AI gets Go wrong” box, gathered in one place, plus the two lists you use whenever the AI reviews or writes code. Use it when you review your own code, or the AI’s.

The chapter sections are quoted unchanged from Chapters 1 to 7, where every command and output was run for this edition (Go 1.27.4). Inside them, words like “this chapter,” “below,” “Break 1” or “the Practice exercise,” and instructions such as “Add these two lines as the last lines of main,” refer to that chapter and its code.

Reviewing the AI’s code

  1. Scope: git status --short lists only what you asked for, never a test file.
  2. Checks: go run ./check, plus go test -race ./... if goroutines share the code.
  3. Diff: git add ., then git diff --staged. Read every line, including changes you didn’t ask for.
  4. Questions: Can you explain it? Does every error path return? Does it match SPEC.md, including status codes? For a server, try it for real with curl.

Deciding on a review suggestion

  1. Do I understand it? If you can’t explain it, you can’t keep it.
  2. Does it fit this project? It must follow your rules: AGENTS.md (Go 1.27, standard library only) and the book’s Must know points, like money in cents.
  3. Do the tests still pass? Make one change at a time and run go test ./... after each.

Each suggestion gets one of four verdicts, the same ones the chapters’ review tables use:

  • Keep: it passes all three questions.
  • Your call: a real improvement, but optional. Keep it if you can explain it (and, if it changes behavior, after updating SPEC.md and the tests); otherwise treat it as skip for now.
  • Skip for now: it may well be right, but it isn’t right for you today, for example because it uses something you can’t explain yet. “Skip for now” doesn’t mean the AI was wrong.
  • Reject: it breaks your rules, the book’s Must know points or a “Where AI gets Go wrong” warning, such as a third-party package, money in a float64 or log.Fatal deep inside a function.

Chapter 5’s review table writes Skip for now as just Skip; they’re the same verdict.

Chapter 1: Learning to Code When AI Can Code

Check it yourself

Where AI gets Go wrong: getting started

AI assistants learned from years of Go code, including a lot of old advice. Watch for these:

  • Old project setup. If the AI tells you to set up a GOPATH folder or set GO111MODULE, that’s how Go worked many years ago. Today you run go mod init in any folder, as you did in this chapter.
  • go get to install tools. Old instructions use go get to install command-line tools. Today, tools are installed with go install, for example go install golang.org/x/tools/gopls@latest. go get is now only for adding packages to a project.
  • Old Go version numbers. The AI may call an older version “the latest.” Trust go version and go.dev, not the AI.
  • Old packages. If you see io/ioutil in AI-written code, that package was replaced years ago. Its functions now live in io and os. The code still compiles, so the compiler won’t warn you, which is exactly why this box exists.

Chapter 2: Your First Program and Your First Test

Check it yourself

Where AI gets Go wrong: numbers, text and tests

  • Money in float64. AI often stores prices as float64 because it looks natural. You’ve seen what 0.1 + 0.2 does. In this book, money is whole cents in an int.

  • string(n) to turn a number into text. AI-written code sometimes does this, and it looks reasonable. Add these two lines as the last lines of main and run it:

        cents := 65
    fmt.Println("Cents: " + string(cents))

    It prints Cents: A, not Cents: 65. string(n) turns a number into the character with that code, and 65 is the code for the letter A. The compiler accepts it, but go vet ./... catches it:

    main.go:12:26: conversion from int to string yields a string of one rune, not a string of digits

    go test ./... refuses to build too, because it runs this vet check automatically. That’s why the Review checks overlap: a mistake one misses, another catches. From Go 1.28 (expected February 2027), the compiler is set to reject this too. To turn a number into text, use fmt.Sprint(n) or strconv.Itoa(n). Delete the two lines when you’re done.

  • Tests written from the code instead of the spec. If you ask the AI to “write tests for this function,” it reads the function and writes tests that agree with it, bugs included. Your tests came from SPEC.md, so they check what you wanted. Keep it that way.

Chapter 3: Lists, Lookups and Loops

Check it yourself

Where AI gets Go wrong: lists and maps

  • Counting on map order. AI-written code sometimes loops over a map and expects a fixed order. It can pass a test several times and then fail at random. Sort the keys.

  • Comparing maps or slices with == or !=. In TestTotalsByCategory, change !maps.Equal(got, want) to got != want and run go test ./...:

    # tracker [tracker.test]
./main_test.go:4:2: "maps" imported and not used
./main_test.go:70:5: invalid operation: got != want (map can only be compared to nil)
FAIL    tracker [build failed]
FAIL

    Go doesn’t compare whole maps or slices with ==. Use maps.Equal and slices.Equal. Change it back.

  • Dropping the result of append. append returns the new slice. Code that writes append(categories, category) without categories = doesn’t compile: append(categories, category) (value of type []string) is not used.

  • Old package paths. golang.org/x/exp/slices and golang.org/x/exp/maps were where these packages lived before Go 1.21. AI trained on older code may still suggest them. If you paste such code, go test ./... stops with:

    main.go:5:2: no required module provides package golang.org/x/exp/slices; to add it:
    go get golang.org/x/exp/slices

    Don’t run that go get. Change the import to slices.

  • Old code that treats maps.Keys as a slice. Code written for the old golang.org/x/exp/maps does keys := maps.Keys(m) and then slices.Sort(keys). With the standard maps package, maps.Keys returns an iterator, not a slice, so Go stops with in call to slices.Sort, S (type iter.Seq[string]) does not satisfy ~[]E. Collect the keys with a loop, as sortedCategories does.

Chapter 4: Modeling Data and Handling Errors

Check it yourself

Where AI gets Go wrong: errors and data

  • Ignoring errors. AI-written code sometimes throws errors away with _ (data, _ := os.ReadFile(path)) or doesn’t look at them at all (os.WriteFile(path, data, 0o644) on a line by itself). It compiles, go vet doesn’t complain, and the program carries on with bad data. The Practice exercise is all about spotting this.
  • %v where %w belongs. As Break 2 showed, the message looks the same, and errors.Is silently stops working.
  • Comparing error text. Code like if err.Error() == "amount must be more than zero" breaks the moment anyone wraps the error or rewords the message. Use errors.Is.
  • Lowercase fields with JSON tags. A field like category string `json:"category"` is unexported, so encoding/json skips it without any error. The file just lacks that field. go vet catches this one: struct field category has json tag but is not exported.
  • Stopping the program from deep inside. log.Fatal or panic inside a function like Load takes the decision away from main. Return the error instead.

Chapter 5: Organizing Code: Packages and Interfaces

Check it yourself

Where AI gets Go wrong: packages and interfaces

  • Changing tests to make them pass. When asked to “make the tests pass,” an AI may edit the tests instead of the code. Always check git status after an implementer task.
  • Vague package names. utils, common, helpers and models say nothing about what’s inside, and they grow into junk drawers. Name a package for what it provides.
  • Stutter. money.FormatMoney or ledger.LedgerTracker repeats the package name. Callers already see it.
  • Interfaces for everything. AI often creates an interface for every type “just in case.” Make one when you have two real versions, as with Storage, and keep it as small as its users need.
  • Value instead of pointer. If TestMemoryStorage used MemoryStorage{} instead of &MemoryStorage{}, the test wouldn’t compile: MemoryStorage does not implement Storage (method Load has pointer receiver). The fix is the &, not changing the receivers.

Chapter 6: From Command Line to Web

Check it yourself

Where AI gets Go wrong: HTTP

  • Third-party routers. Older code often uses gorilla/mux, chi or gin for routing by method and path. Since Go 1.22, http.ServeMux does that with patterns like "POST /expenses".
  • Checking the method by hand. Code like if r.Method != http.MethodPost { ... } inside a handler is the old way. It works, but patterns make it automatic, including the 405 response.
  • No return after http.Error. The handler keeps running and tries to write a second response. Go logs http: superfluous response.WriteHeader call and the client gets a confusing reply.
  • Ignoring encode and decode errors. json.NewEncoder(w).Encode(v) returns an error too. At minimum, log it.
  • Data races. Every request runs at the same time as the others, so two requests can change the Tracker at once. Your tests send one request at a time, so they don’t notice. Chapter 7 is about exactly this.

Chapter 7: A Taste of Goroutines

Chapter 7 has no “Check it yourself” list. Its Review checklist is the “Questions for this kind of change” from Review the AI’s work, plus the first question for the import feature:

  • Is every access locked? Add writes expenses, while Totals and Save read it. All three must lock, not only the one that writes. Break 1 below shows why.
  • Does Save hold the lock while writing the file? Yes, and that’s on purpose: it also stops two saves from writing expenses.json at the same time. That’s what turned the file into broken JSON in the opening experiment.
  • Why is the amount check before the lock? It doesn’t touch shared data, so there’s no need to make other goroutines wait for it. Keep locked sections short.
  • Is Open still right? It builds a new Tracker with mu left at its zero value, which is an unlocked mutex, ready to use. Must know #4 in action.
  • How many goroutines start, and does every one of them finish? Here, one per file, and each sends exactly one result. The receiving loop runs once per file, even after an error. If it returned at the first error, the remaining goroutines would wait forever to send. That’s the goroutine leak from the box.

Where AI gets Go wrong: goroutines

  • Locking only the writes. As Break 1 showed, reads need the lock too.
  • Forgetting to unlock. A Lock() without a matching Unlock() on every path makes the next goroutine wait forever, and your program hangs. defer mu.Unlock() right after Lock() prevents it.
  • t.Fatal inside a goroutine. It may only be called from the test’s own goroutine. Use t.Errorf in goroutines.
  • The old WaitGroup pattern. AI often writes wg.Add(1) and go func() { defer wg.Done(); ... }(). It works, but wg.Go does the same with less to get wrong.
  • Goroutines that never finish. A goroutine blocked forever on a channel nobody reads is a goroutine leak. You’ll see why that matters in the next loop.
